# Production data migration — 2026-09-26

## Scope

A one-time migration copied the established local PersonalHub product data from the isolated PostgreSQL 16 Compose database into production. It was a selective data import, not a database replacement. Production identity, authentication, security, and Prisma migration state remained authoritative.

The source was the `personalhub` database in the healthy `personalhub-overhaul-postgres-1` service, backed by the named volume `personalhub-overhaul_personalhub_overhaul_pg`. The legacy SQLite/port-3001 stack was not used or changed.

## Table classification

Migrated product-data tables:

- `Project`
- `Task`
- `Assignment`
- `Note`
- `Tag`
- `_AssignmentTags`
- `_NoteTags`
- `_TaskTags`

Preserved production security tables:

- `Owner`
- `Session`
- `ApiToken`
- `LoginThrottle`

Preserved production schema metadata:

- `_prisma_migrations`

These classifications account for every table in the application schema.

## Safety artifacts

Before the import, a full custom-format production dump was uploaded to:

`s3://personalhub-production-210855481769-pg-backups/postgresql/manual/pre-local-data-migration/personalhub-pre-local-data-migration-20260926T111436Z.dump`

The verified object size is 22,680 bytes. It includes the production owner and authentication state and is retained as the rollback anchor.

A verified full custom-format source snapshot is retained outside Git under the operator's protected `~/.local/share/personalhub-migrations/` directory with mode `0600`. Temporary selective archives were removed from the controller and EC2 after validation.

## Method and rehearsal

The migration used a PostgreSQL custom-format, data-only archive containing exactly the eight product-data tables. The archive excluded all security tables and `_prisma_migrations`.

Before production mutation, the archive was restored with `pg_restore --single-transaction --exit-on-error` into a disposable PostgreSQL 16 database with the current Prisma migrations and pre-existing owner, session, API-token, and login-throttle sentinels. The rehearsal proved:

- complete row-count and full-row fingerprint parity;
- preserved IDs, timestamps, scalar values, nullability, and relationships;
- foreign-key and unique-constraint integrity;
- unchanged target security sentinels and migration metadata;
- successful Prisma Client reads;
- no database sequences requiring correction because product IDs are text values generated by the application.

## Rollback strategy

Rollback is intentionally manual and is not part of routine deployment:

1. stop only the PersonalHub application;
2. download the retained pre-migration S3 dump through an authorized operational path;
3. restore that full custom-format dump into the production `personalhub` database using a reviewed replacement procedure;
4. restart PersonalHub;
5. verify the owner login, all three container health checks, internal and public `/api/health`, migration count, and zero AWS ingress drift.

Rollback was not executed because all migration validations passed. Scheduled backup automation and restore rehearsal remain separate future work.
